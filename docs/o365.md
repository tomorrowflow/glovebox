# Source: Office 365 mail

The `o365_mail` source serves the operator's work mail, the inbox of the rolling 30 days, as items with handles and permitted fields only, read-only and live (ADR 0003, ticket 16). It is implemented and tested against a stand-in for Microsoft's authority and Graph. **It has not been run against a real work account: that is the operator's acceptance run below.** Until it passes the source is not delivered, and if the employer does not consent it stays `blocked` and is recorded as that, never worked around (ADR 0003: workplace restrictions are never bypassed).

## The access method, and why

The gate reads the mailbox through **Microsoft Graph** (`GET /me/mailFolders/inbox/messages`), the provider's official API, signed in as the operator with a **delegated `Mail.Read` permission**.

| Option | Verdict |
|---|---|
| **Graph, with `msal` for sign-in and token refresh, and the standard library for the one `GET`** (chosen) | `msal` is Microsoft's own Python authentication library ([microsoft-authentication-library-for-python](https://github.com/AzureAD/microsoft-authentication-library-for-python)), version 1.39.0 on the package index on 27 Nov 2026, with `requests` as its only HTTP dependency. It does the parts that are easy to get wrong (device code flow, token cache, refresh, the authority's error vocabulary). The Graph call is one fixed `GET` with a bearer token, which the gate sends the same way as every other source request: no proxy from the environment, no redirect followed, bounded size and time. MSAL's own traffic to the authority is not under those rules: it goes through `requests`, which follows the environment's proxy settings and `REQUESTS_CA_BUNDLE`, so a host that needs a proxy to reach `login.microsoftonline.com` can set it. |
| `msgraph-sdk` | The official Graph SDK, 1.65.0 on the index. Resolving it against `constraints.txt` adds about 30 packages (`aiohttp`, `httpx`, the Kiota family, `azure-identity`, OpenTelemetry), all async, for one request. Its errors are objects that carry Graph's message text, which the gate must never keep. Not adopted; revisit if the gate ever needs more than reading inbox messages. |
| `O365` (python-o365) | A community wrapper, 2.1.11 on the index. It brings its own scope handling, and its defaults and convenience calls include mail that writes. Not adopted for a source whose point is a credential that cannot write. |
| IMAP with OAuth | The IMAP permission is `IMAP.AccessAsUser.All`, full access to the mailbox, and IMAP read access is not a credential boundary. Not provider-enforced read-only. Not adopted. |

Only version numbers and dependency footprints were checked (the package index and `pip` dependency resolution, 27 Nov 2026); the libraries' code was not audited beyond what the tests exercise. Re-check when upgrading `msal`.

## Permissions, and what makes read-only provider-enforced

The login asks for exactly one permission, **`Mail.Read` (delegated)**, and MSAL adds the sign-in scopes `openid` and `profile` and `offline_access` (the refresh token). Together they:

- let the gate read the operator's messages, **including their body text**, which the quarantined classifier needs. `Mail.ReadBasic` is narrower but leaves the body out, so the classifier would have nothing to judge: `Mail.Read` is the narrowest permission that allows classification of the body.
- do **not** allow sending, drafting, changing, moving, flagging or deleting mail. Those need `Mail.ReadWrite` or `Mail.Send`, which the gate never asks for.
- do **not** mark a message read: a `GET` of a message does not, and nothing else is called.

A delegated token is limited by what the operator may do, and by this permission. Because the credential itself cannot write, every account entry reports `read_only_enforcement: provider`, the one source for which it does.

The gate does not take that on trust. At every sync it reads the permissions the authority recorded for the token it is about to use, and **refuses a token that carries any permission other than the sign-in scopes and read permissions** (`Mail.ReadWrite`, `Mail.Send`, `Calendars.ReadWrite`, `Directory.AccessAsUser.All` and the like): the account is `blocked` and nothing is asked of Graph. This matters when the app registration has been consented to more than the gate asks for, because what a token carries is what the authority records for it, not what the gate asked. Other read permissions (`User.Read`, `Calendars.Read`) are accepted. `glovebox o365-login` applies the same check and refuses to store such a login.

What provider-enforced does not say: the token can read the whole mailbox, not only the inbox the gate reads; and agents never receive it (ADR 0004).

## What the employer has to grant

Reading the work mailbox as an app needs the tenant's consent. This is the part that can block the source indefinitely.

- **Microsoft's default** does not require an administrator for delegated `Mail.Read`, but many employers turn user consent off or limit it to low-risk permissions. Then **an administrator must grant consent** for the app: in the Entra admin center, Enterprise applications, the app, Permissions, "Grant admin consent for the tenant", for the delegated Microsoft Graph permission `Mail.Read` only.
- **The app registration.** You need an application (client) ID. Either the employer's IT registers one in the tenant, or you register one (Entra admin center, App registrations, New registration; supported account types as the employer requires). In both cases: *Authentication*, "Allow public client flows" = Yes (the device code flow needs it); *API permissions*, Microsoft Graph, delegated, **`Mail.Read` and nothing else** (remove the default `User.Read` if you like; the gate does not need it).
- **Do not use another app's client ID** (a Microsoft tool's, a mail client's) to get around a refusal. That is bypassing the employer's consent policy, which this project never does (ADR 0003).
- **Conditional Access** or a device policy can still refuse the sign-in even with consent (for example a rule that blocks the device code flow, or requires a managed device). That is also a refusal: ask the employer, or record the source as `blocked`.

If the employer will not consent, stop here: the source is `blocked`, the ticket closes as blocked, not as delivered.

## Setting the account up

Run on the gateway host as the gateway's user, with `<checkout>/.venv/bin/glovebox`.

1. **Get consent and a client ID** as above.
2. **Sign in.** The command prints a code and a page; open the page in any browser, enter the code and sign in with the work account. It asks for `Mail.Read` only and writes the login to a file only you can read (mode `0600`, ADR 0004):

   ```sh
   glovebox o365-login --client-id <client-id> --tenant <tenant-id-or-domain> \
     --credentials ~/.config/glovebox/o365-work
   ```

   `--tenant` defaults to `organizations`; `--authority` takes a full authority URL instead (a sovereign cloud). If consent is missing the command prints Microsoft's error name and its `AADSTS` code (65001 is "consent required", 90094 "admin approval needed") and writes nothing.
3. **Add the account.** `<name>` is your own label; agents never see it. The source is the Graph endpoint, which must be `https`:

   ```sh
   glovebox account add <name> --kind o365_mail --source https://graph.microsoft.com/v1.0 \
     --credentials ~/.config/glovebox/o365-work
   ```

4. **Issue a token** for the account (`glovebox token issue --account <name>`), as for any source.
5. **Check what agents see:** `GLOVEBOX_CHECK_TOKEN=<token> .venv/bin/python scripts/imessage_check.py --url <the MCP URL>` (the script is named for iMessage but asks for any account). Expect `read_only_enforcement: provider`, status `current`, and items that carry only handles and permitted fields.

**The credentials file** holds the client ID, the authority and MSAL's token cache, which contains a refresh token. **The gate rewrites it** whenever MSAL refreshes the cache, because Microsoft replaces the refresh token as it is used; it does so atomically and keeps the mode `0600`. So the file must be in a directory the gateway's user can write, and a backup of it goes stale. The gate refuses a file open to group or others. To see which permissions the stored token carries (it prints no secret):

```sh
python3 -c "import json,sys; c=json.loads(json.load(open(sys.argv[1]))['token_cache']); \
print([a['target'] for a in c['AccessToken'].values()])" ~/.config/glovebox/o365-work
```

**Withdrawing access.** The employer or the operator can revoke the app's consent or the user's sessions at any time (Entra admin center, or the operator's My Account page). The next sync then fails at the authority and the account is `blocked`; other accounts are unaffected. To restore access, get consent again and run `glovebox o365-login` once more to the same file.

## What an item is

- The **inbox** only, messages received in the last 30 days, newest first. Sent items, drafts, deleted items and **other folders are not read**: mail that a rule moves out of the inbox is not seen. Reading more folders is a choice for another ticket.
- `sender_handle` stands for the sender's address (lowercased) and `thread_handle` for Graph's `conversationId`; the gate turns both, and the message ID, into opaque handles. Message IDs are requested as immutable IDs, so a message keeps its handle when it is moved to another folder.
- `read_status` is Graph's `isRead`, `has_attachments` is `hasAttachments`; nothing about an attachment is read. Names, subjects, recipients, categories, previews and every other property are never selected (`o365.FIELDS`).
- The subject and the body (as plain text, cut at 16,000 characters) go to the quarantined classifier in memory and nowhere else; the gate stores, logs and serves none of it (ADR 0004). A message that cannot be understood (no ID, no sender, an impossible time, a non-boolean attachment flag) is skipped and counted: the account is `incomplete`. So is any excess over 5,000 messages in the window, which is cut to the newest.
- Like every source, the window is read at every tool call that reads, in pages of 25 and within 60 seconds in all, over the access token that MSAL keeps in the cache (about an hour; a refresh happens when it runs out).

## Failure behavior

| What happens | Account status |
|---|---|
| The login is missing, unreadable, not a Microsoft login, or has never signed in | `blocked` |
| The authority refuses the refresh token (`invalid_grant`, `interaction_required`, `consent_required`, `invalid_client`, `unauthorized_client`, `access_denied`): consent withdrawn or never given, the token revoked or expired, a policy | `blocked` |
| Graph answers 401 or 403 | `blocked` |
| The token carries a permission that could write, or the authority did not say what it carries | `blocked` |
| The Graph endpoint is not `https` | `blocked`; nothing is sent |
| The authority or Graph is down, throttled (429), answers 5xx, resets, times out, redirects, sends a body that is not the expected JSON, or links to another host | `stale`; the fixed `source_unavailable` error and the last good sync time. The next successful read makes it `current` again |

Errors carry no detail. Neither Graph's nor the authority's error text is read into an exception, and **MSAL's own log output is switched off** (it logs what the authority answered), as is that of `requests` and `urllib3`: no upstream text reaches the gate's log. A link to another host in a response (`@odata.nextLink`) is never followed, so the token goes only to the endpoint of the account. When Graph refuses a token (401 or 403), the gate also drops its cached access tokens, so the next sync asks the authority for a new one instead of waiting out the hour. A message in the inbox without a sender (Graph leaves `from` out of some drafts and system messages) is skipped and counted, so such a message keeps the account `incomplete`. The two commands that talk to the operator (`o365-login` and its prompt) print Microsoft's sign-in message and error name on the operator's own terminal; that text is not served to agents or logged by the gate. The gate does not retry or wait out throttling: a throttled read is a `stale` account, and the next tool call tries again.

## External inference stays off for this account

The classifier reads the text of every item, and that text is work mail. **Local inference is the default; external inference is off for this account unless the operator turns it on explicitly** (ADR 0002): only accounts named in `inference.external.accounts` of the classifier configuration send their text to an external provider (`docs/inference.md`). Do not list this account without checking what your employer's policy allows for work mail. There is no setting that turns it on by itself, and a test checks that an unlisted `o365_mail` account sends nothing to the external stand-in.

## The test tier

The stand-in for the work mail at `standins:9103` serves a fixture document and cannot be read by an `o365_mail` account: this source speaks Microsoft's protocols (OIDC discovery, OAuth token and device code endpoints, Graph) over https, which MSAL requires. The tests use their own stand-in, `tests/o365.py`: one TLS listener on loopback with a certificate generated for the run, which a test makes the gate trust through `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` (the gate has no setting for it). It rotates refresh tokens as Microsoft does, records every request, and injects each fault with the hostile corpus in its status line, headers and body. `tests/test_o365.py` drives it through a real MCP client: the mapping, the requests the gate makes (only reads, only the permissions above), rotation and saving of the login, consent missing or withdrawn, every outage and malformed response, the hostile corpus in every message property, ID and error text, and external inference. A stand-in never counts as delivering the source (ADR 0003).

## Acceptance (operator-only)

Run once at merge, in an isolated gate: a scratch database, another port and a checkout of your own, not the shared test tier. Use a new login file for the run.

1. **Consent.** Get it as above. If it is refused, skip to the end and record `blocked` with the reason (the AADSTS code or the employer's answer).
2. **Snapshot what must not change.** In Outlook on the web, note the unread count of the inbox and which messages are unread (open nothing).
3. **Sign in and add the account** (steps 2 and 3 above), then start the isolated gate and issue a token:

   ```sh
   export GLOVEBOX_DB=$(mktemp -d)/acceptance.db GLOVEBOX_PORT=18765
   <checkout>/.venv/bin/glovebox o365-login --client-id <id> --tenant <tenant> --credentials <file>
   <checkout>/.venv/bin/glovebox account add work --kind o365_mail \
     --source https://graph.microsoft.com/v1.0 --credentials <file>
   export GLOVEBOX_CHECK_TOKEN=$(<checkout>/.venv/bin/glovebox token issue --account work 2>/dev/null)
   <checkout>/.venv/bin/glovebox serve &
   ```

4. **Live mail appears as items.** `<checkout>/.venv/bin/python scripts/imessage_check.py --url http://127.0.0.1:18765/mcp`. Expect status `current`, a recent last sync, `read_only_enforcement: provider`, and items that carry only handles, minute-precision `received`, `read_status`, `has_attachments` and the semantic fields, with no text. The count matches the inbox's messages of the last 30 days.
5. **The granted permissions are read-only.** Run the permission check above on the login file: the list holds `Mail.Read` and sign-in scopes (and at most other read permissions), nothing with `Write`, `Send` or `AccessAsUser`. Also check the app's permissions in the Entra admin center.
6. **A newly received message.** Send yourself a mail from elsewhere and run step 4 again: one more item with a newer `received` time and `unread`.
7. **Reading leaves messages unread.** Compare Outlook's unread count and the unread messages with step 2: they have changed only by what you received or read yourself. Do not open the messages between steps 2 and 7.
8. **Withdrawal.** Optionally revoke the app's consent or your sessions and run step 4: the account is `blocked` and the exit status 1.
9. Stop the gate (`kill %1`) and delete the scratch directory.

Record the result on the ticket: delivered (steps 1 to 7 pass), or `blocked` with the reason. A stand-in run is never a delivery.
