# AGENTS.md

Glovebox is one Python service on the official MCP Python SDK, with SQLite for state (ADR 0005). Agents connect over Streamable HTTP.

## Commands

Python 3.12 or newer. Run from the repository root.

| Task | Command |
|------|---------|
| Install (creates `.venv`, pins from `constraints.txt`) | `python3 -m venv .venv && .venv/bin/pip install -c constraints.txt -e ".[dev]"` |
| Test | `.venv/bin/python -m pytest` |
| Lint and format check | `.venv/bin/python -m ruff check . && .venv/bin/python -m ruff format --check .` |
| Format | `.venv/bin/python -m ruff format .` |
| Type check | `.venv/bin/python -m mypy` |
| Run the service | `.venv/bin/glovebox` |

The service listens on `127.0.0.1:8765`, MCP endpoint `/mcp`; override with `GLOVEBOX_HOST` and `GLOVEBOX_PORT`. It serves only loopback `Host` headers and answers `421` to any other; `GLOVEBOX_ALLOWED_HOSTS` (comma-separated exact `host[:port]`, no wildcard, a wildcard stops the start) adds more, for a reverse proxy in front of it. It answers `401` to any request without an active agent token, checked against the database on every request, so keep it on loopback. `GLOVEBOX_DB` is the SQLite file (default `glovebox.db`), shared with the operator's command line.

The operator sets accounts and tokens up locally, outside MCP, with `.venv/bin/glovebox account add|list|remove` and `.venv/bin/glovebox token issue|list|revoke` (`glovebox --help`). `token issue` prints the token value once on stdout and stores only its digest. An account's credentials live in a file that only the gateway's user may access (mode `0600`): `account add --credentials FILE` and the service itself refuse a file open to group or others (ADR 0004). The throwaway and test stacks start the gate as `glovebox serve --bootstrap-fixture`, which registers a `fixture` account for the mail stand-in (`GLOVEBOX_STANDIN_MAILBOX_MAIL`, or `GLOVEBOX_MAIL_FIXTURE` for a file) and a token with the value of `GLOVEBOX_FIXTURE_TOKEN`; tests use the same commands through `tests/conftest.py`. The second fixture source kind, `fixture_messenger` (`account add NAME --kind fixture_messenger --source FILE_OR_URL`; tests pass `kinds=` to `start_gate`), reads a document of `conversations` with `messages`: its items are served by the same tools as mail, with the conversation handle in `thread_handle`. The `imessage` kind (`docs/imessage.md`, `src/glovebox/chatdb.py`) reads either that document from the iMessage stand-in over `GET /` (a bridge on another host needs a credentials file holding its bearer token, sent only over https; only loopback goes without, see `bridge_problem` in `sources.py`) or, with a file path as `--source`, the Mac's Messages database opened read-only; tests build a database file with `MessagesDb` in `tests/test_imessage.py`. Source adapters take the window start and the clock in `fetch(since, now)`. The local Messages database is `stale` after `GLOVEBOX_IMESSAGE_MAX_SILENCE_HOURS` (default 72, `0` off) without any activity in it; tests that need a `current` database give it a recent row (see `MessagesDb.receive(..., sent_by_me=True)` in `tests/test_imessage.py`). Each account entry carries `read_only_enforcement` (`gateway` or `provider`, from `READ_ONLY_ENFORCEMENT` in `sources.py`). `GLOVEBOX_FIXED_NOW` (an ISO 8601 time with a UTC offset) pins the clock the 30-day mail window is measured from; tests set it so fixture mail does not age out, and a real deployment leaves it unset.

The calendar source kind, `fixture_calendar` (`account add NAME --kind fixture_calendar --source FILE_OR_URL`; `src/glovebox/calendars.py`), reads a document with an `account`, an optional IANA `timezone` and a list of `events`; the `mailbox-calendar` and `o365-calendar` stand-ins serve that shape. An event needs `id`, `start` and `end`; `all_day`, `timezone`, `status` (`confirmed`, `tentative`, `cancelled`), `transparency` (`opaque`, `transparent`), `participation` (`accepted`, `tentative`, `needs_action`, `declined`), `recurrence` (`freq` daily, weekly, monthly or yearly, with `interval`, `count`, `until`, weekly `by_day`) and `exceptions` are optional, and no other key is read. Its accounts are read by the three calendar tools (`get_availability`, `list_events`, `list_overlaps`, one read operation each) and by no item tool, and the item tools never read them. The 90-day look-ahead starts at the gate's clock; `GLOVEBOX_FIXED_NOW` pins it as it does the mail window, and tests move it with `now=`. Events are stored one row per occurrence (`events` table, permitted fields only), keyed by a JSON list of the UID (and the day, for an occurrence of a recurring event) so that no UID can pass for another's. At most 2000 events are kept per account, the earliest first: the account is then `incomplete`, and `get_availability` reports the time from the first dropped event on as `unknown` and never `free`. Two different events that share a UID are both kept, each identified by its times and status and not by its place in the document, so reordering the entries keeps each handle on its event (an event whose sibling is removed goes back to the plain UID identity, and so to another handle). Daily and weekly series with no count are expanded from near the look-ahead, however far back they began; any other series that needs more than 20,000 candidate dates to reach it (a monthly series from the year 1, say) counts as skipped and makes the account's availability `unknown` across the whole look-ahead, never `free`. The source hands the store events with their real times, and the store cuts them to the look-ahead, so an event's identity never depends on the clock. A range is cut to the look-ahead by the store itself, and a range with no time left selects nothing.

The `o365_calendar` kind (`docs/office365-calendar.md`, `src/glovebox/o365.py`) reads the work calendar from Microsoft Graph's `calendarView`, which expands recurring events itself (read twice: timed events in UTC, so the repeated hour at the end of summer time is never ambiguous, and all-day events in the calendar's zone), with a delegated `Calendars.Read` token and nothing else, so its `read_only_enforcement` is `provider`, the only kind that is. `account add NAME --kind o365_calendar --source https://graph.microsoft.com/v1.0 --credentials FILE` takes a file made by `glovebox o365 login --credentials FILE --client-id ID --tenant-id ID [--timezone IANA]` (the device code flow, through `msal`); the file is JSON (`client_id`, `tenant_id`, `timezone`, optional `authority`, and `msal`'s `token_cache`) and the gate rewrites it, mode `0600`, when a refresh rotates the cache. A missing, refused or withdrawn sign-in, `401` and `403` are `blocked`; everything else that fails is `stale`. `msal` only talks to https authorities, so `tests/test_o365.py` runs a TLS stand-in of the sign-in service and Graph (`tests/o365_standin.py`, a certificate made per run, trusted through `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE`), not the canned `o365-calendar` stand-in, which serves the `fixture_calendar` document shape. Graph events go into `hostile_graph_events` (`tests/hostile.py`) the same way.

`GLOVEBOX_CLASSIFIER_CONFIG` names the operator's classifier configuration, a JSON file with `topics` (`id`, `name`, `description`; IDs match `^[a-z][a-z0-9_]{0,23}$`, `other` and `unknown` are reserved), an optional `deadline_range` (`from`, `to`, minute timestamps) and `inference` (`backend`, `profile`, `local`, `external`); it is read at startup. With no file at all, or with a file and no `inference` section, classification runs on local inference (an empty topic list without a file), and `"inference": {"backend": null}` is how the operator turns the classifier off, so that every item is `unavailable`. Local inference is an OpenAI-compatible server on the gateway host (Ollama by default, `src/glovebox/inference.py`, `docs/inference.md`). `inference.external` (`url`, `model`, `api_key_file`, `accounts`) sends only the listed accounts' text to an external provider; there is no fallback in either direction. The backend `stub` is the deterministic stand-in for a model; `GLOVEBOX_STUB_CLASSIFIER_SCRIPT` and `GLOVEBOX_STUB_CLASSIFIER_PROBE` are test-only controls of it (see `src/glovebox/stub.py`). `GLOVEBOX_STANDIN_INFERENCE_LOCAL` and `_EXTERNAL`, set by the throwaway and test stacks, replace the `url` of `local` and `external`. Changing the topic list or an account's inference settings makes that account's stored classifications stale. The `list_topics` tool is one more read operation a token can be limited to; tokens issued before it existed do not name it and must be reissued to use it. CI (`.github/workflows/ci.yml`) runs the install, lint, type check and test commands above.

Dependencies are pinned exactly in `pyproject.toml`; `constraints.txt` pins the full set. When you change a dependency, update both.

## Environments

Bring up a throwaway stack for your ticket with `python3 scripts/env.py up`, then `check`, `reset` and `down`. It runs the gate in rootless Docker with a stand-in for every outside service and a seeded fictional fixture cast. Never put real data in a fixture. Test and production run natively on the Mac mini, with no Docker. Tiers, the test environment and the production runbook are in `docs/environments.md`. Tickets and agents never administer production; an agent reaches only its gate, with a scoped operator-issued token.

## Testing

Acceptance tests drive the service through MCP tool calls with a real MCP client over HTTP (ADR 0006). Tests live in `tests/`.

Fixture mail in tests is dated within the 30 days before the pinned `NOW` in `tests/conftest.py`; pass `now=` to `start_gate` to move the clock.

Every new field or tool extends the reusable hostile-corpus helpers: put corpus strings in the new attacker-writable fields of `hostile_mail_fixture` (`tests/hostile.py`), add any new tool to `OK_CALLS` and any new parameter to `hostile_calls` (`tests/hostile.py`), add any new response channel to `observe_gate` (it already includes the gate's log, which `RunningGate.log` captures), and check new output schemas with `closed_schema_problems` (`tests/schema.py`). `assert_no_corpus` then covers every channel. Calendar tests (`tests/test_calendar.py`) use `hostile_calendar_fixture` the same way. Responses leave the gate only through `output.release`, the one output validator.

Inference tests (`tests/test_inference.py`) run the gate against the canned inference stand-ins (`deploy/standins`, started in the test process and recording what they are sent), with `GLOVEBOX_STANDIN_INFERENCE_LOCAL` and `_EXTERNAL` pointing at them; a small scripted server makes the errors a stand-in cannot.

Classifier tests (`tests/test_classifier.py`) drive the stub with a script file that maps a marker in an item's text to the raw output it returns, so a test chooses what the "model" says. Pass `extra_env=` to `start_gate`; `RunningGate.log` is everything the service printed, for "nothing in logs" checks. The classifier's inputs and raw output are never served, logged or stored; those tests check the log and the stored files as well as every response.
